# Device credential storage and lifecycle

## Storage contract
- Each provisioned device receives a unique `key_id` and a high-entropy secret generated by a trusted provisioning service.
- The database stores only a one-way verifier (`secret_hash`), never the raw secret.
- Raw secrets are shown or delivered only during controlled provisioning; they must not be written to logs, analytics, crash reports, or support exports.
- `key_id` is an identifier, not an authenticator. Requests must prove possession of the secret using a reviewed challenge/HMAC protocol with freshness and replay protection.
- Credential records are scoped to one device and can be revoked independently.

## Rotation and revocation
1. Generate a replacement secret in the provisioning trust boundary.
2. Store its verifier under a new key identifier and allow a bounded overlap only if the protocol supports it safely.
3. Confirm the device has adopted the new credential.
4. Revoke the old credential and record an audit event.
5. On suspected compromise, revoke immediately; do not rely on app logout.

## Not implemented yet
This schema is not an authentication implementation. Device API routes must remain unavailable until request signing, nonce/timestamp validation, constant-time verifier comparison, rate limiting, credential provisioning, and audit handling are implemented and tested. The firmware must keep local protection independent of cloud authentication.
